# InkyPi Bluetooth Control Protocol

This document defines the BLE GATT protocol used by InkyPi so that mobile apps
(e.g. the InkyPi Flutter companion) can configure the device, manage plugins,
provision Wi-Fi, and upload images **without requiring an existing Wi-Fi
connection**.

The protocol is intentionally small and JSON-based so it is straightforward to
implement on any BLE central (Android, iOS, Linux, browser via Web Bluetooth).

---

## Topology

```
[ Phone (BLE central) ]  ── GATT ──▶  [ inkypi-ble.service (peripheral) ]
                                                │
                                                │ http://127.0.0.1
                                                ▼
                                     [ inkypi.service (Flask) ]
                                                │
                                                ▼
                                       [ E-Ink display ]
```

`inkypi-ble.service` runs as a separate systemd unit. It exposes a single GATT
service with a small set of characteristics. For most operations it translates
the BLE command into an HTTP call against the local Flask app (so any logic
already implemented for the web UI is automatically available over BLE).

Wi-Fi provisioning and connectivity status are handled directly by the BLE
service via `nmcli` (NetworkManager) because they may need to work *before*
Flask has network connectivity.

---

## GATT services and characteristics

Service UUID:
```
4e6b9c80-1d3a-4e8a-9b7e-1f7b3c5a0000
```

All characteristics live under this service. UUIDs are derived by varying the
last 4 hex digits.

| Char | UUID suffix | Properties             | Purpose                                  |
|------|-------------|------------------------|------------------------------------------|
| INFO | `0001`      | read, notify           | Device info JSON (auto-updated)          |
| CMD  | `0002`      | write                  | JSON command from app                    |
| RESP | `0003`      | notify                 | JSON response (fragmented if needed)     |
| WIFI | `0004`      | write, notify          | Wi-Fi scan / connect / status            |
| UPC  | `0005`      | write, notify          | Upload control (start / finish / status) |
| UPD  | `0006`      | write-without-response | Upload data chunks                       |

MTU is negotiated at connection time. The peripheral advertises support up to
512 bytes (NetworkManager default on Pi is typically 247). The app must call
`requestMtu(512)` (Android) or rely on the iOS default (185).

---

## Common message format

All JSON payloads on `CMD`, `RESP`, `WIFI`, `UPC` follow this envelope:

```json
{
  "id": "<client-supplied request id>",
  "op": "<operation name>",
  "data": { ... }     // request-specific fields
}
```

Responses use the same envelope with `"status": "ok" | "error"` and either
`"data"` or `"error"` set.

### Response fragmentation

Responses on `RESP` may exceed the MTU. They are split into fragments framed
as:

```
[ 1 byte: flags ][ 2 bytes: seq (big-endian) ][ payload bytes ]
```

| Flags bit | Meaning              |
|-----------|----------------------|
| `0x01`    | More fragments       |
| `0x02`    | Last fragment        |
| `0x04`    | Error (final frame)  |

The app concatenates payload bytes in `seq` order. The complete payload is
UTF-8 JSON.

## INFO characteristic

Read or subscribe to receive device status. The value is a JSON object:

```json
{
  "name": "InkyPi-A7C2",
  "version": "1.0.0",
  "wifi": {
    "mode": "client" | "ap" | "offline",
    "ssid": "HomeNetwork",
    "ip": "192.168.1.42"
  },
  "ap": {
    "ssid": "InkyPi-A7C2",
    "password": "<8-char autogenerated>",
    "ip": "192.168.4.1"
  },
  "display": {
    "resolution": [800, 480],
    "current_plugin": "weather",
    "last_refresh": "2026-05-26T10:14:32+08:00"
  },
  "flask_reachable": true
}
```

The peripheral pushes a fresh notification whenever any of these values
change.

## CMD / RESP — control commands

The app writes a JSON command to `CMD`. The peripheral processes it and emits
one (possibly fragmented) JSON response on `RESP` with the same `id`.

### Supported operations

| op                          | data fields                                                       | Bridged to |
|-----------------------------|-------------------------------------------------------------------|------------|
| `list_plugins`              | —                                                                 | local read of `device.json` |
| `list_playlists`            | —                                                                 | local read of `device.json` |
| `get_settings`              | —                                                                 | local read of `device.json` |
| `save_settings`             | full settings dict (matches `/save_settings` form fields)         | `POST /save_settings`       |
| `display_plugin_instance`   | `playlist_name`, `plugin_id`, `plugin_instance`                   | `POST /display_plugin_instance` |
| `create_playlist`           | `playlist_name`, `start_time`, `end_time`                         | `POST /create_playlist`     |
| `update_playlist`           | `playlist_name`, `new_name`, `start_time`, `end_time`             | `PUT /update_playlist/...`  |
| `delete_playlist`           | `playlist_name`                                                   | `DELETE /delete_playlist/...` |
| `delete_plugin_instance`    | `playlist_name`, `plugin_id`, `plugin_instance`                   | `POST /delete_plugin_instance` |
| `set_plugin_order`          | `order` (list of plugin ids)                                      | `POST /api/plugin_order`    |
| `set_apikey`                | `entries` (list of `{key,value,keepExisting}`)                    | `POST /api-keys/save`       |
| `redisplay_last`            | —                                                                 | `POST /display_plugin_instance` for the last playlist entry (errors if last display was a one-off update) |
| `reboot`                    | —                                                                 | `POST /shutdown {reboot:true}` |
| `shutdown`                  | —                                                                 | `POST /shutdown`            |

Plugin instances with binary settings (e.g. uploaded images) cannot be created
through `CMD` alone — use the upload flow below and pass the returned
`upload_id` as part of the plugin settings dict.

## WIFI characteristic — provisioning

Wi-Fi runs on its own characteristic so a client can manage networking even
when Flask isn't running yet.

### `op: "scan"`

Request:
```json
{ "id": "1", "op": "scan" }
```
Response (single fragment unless many networks):
```json
{
  "id": "1",
  "status": "ok",
  "data": {
    "networks": [
      { "ssid": "Home", "signal": -52, "security": "WPA2" },
      { "ssid": "Cafe Free", "signal": -73, "security": "OPEN" }
    ]
  }
}
```

### `op: "connect"`

Request:
```json
{
  "id": "2",
  "op": "connect",
  "data": { "ssid": "Home", "password": "hunter2" }
}
```
Response: `status: "ok"` with `data: {"ip": "192.168.1.42"}` on success,
`status: "error"` with `error: "..."` otherwise. The peripheral will also push
a new INFO notification.

### `op: "forget"`

Request:
```json
{ "id": "3", "op": "forget", "data": { "ssid": "Home" } }
```
Removes the saved connection profile.

### `op: "status"`

Returns the same `wifi`/`ap` block as INFO.

### `op: "list_saved"`

Returns the SSIDs of every saved Wi-Fi profile (excluding the AP fallback).

Request:
```json
{ "id": "5", "op": "list_saved" }
```
Response:
```json
{ "id": "5", "status": "ok", "data": { "ssids": ["Home", "Cafe Free"] } }
```

### `op: "ap_enable"` / `op: "ap_disable"`

Manually toggles the access-point fallback. Normally `inkypi-netd.service`
toggles this automatically when no upstream Wi-Fi is available.

## Upload flow — UPC + UPD

Image uploads exceed the BLE MTU, so they use a dedicated two-characteristic
streaming protocol.

### 1. Client → UPC: start

```json
{
  "id": "u1",
  "op": "start",
  "data": {
    "name": "sunset.jpg",
    "size": 81342,
    "sha256": "0bc4...",
    "plugin": "image_upload",
    "playlist": "Default",          // optional — adds to playlist when present
    "instance_name": "Sunset photo",// optional — required if playlist is set
    "display_now": true             // optional — pushes to display after upload
  }
}
```

Peripheral responds on UPC:
```json
{
  "id": "u1",
  "status": "ok",
  "data": { "upload_id": "abc123", "chunk_size": 244 }
}
```

`chunk_size` is the maximum number of payload bytes per UPD write (MTU minus
3-byte ATT header minus 5-byte chunk header).

### 2. Client → UPD: data chunks

Each write to UPD is binary:
```
[ 1 byte: 0x02 (DATA) ][ 4 bytes: seq (big-endian) ][ payload bytes ]
```
- `seq` starts at 0 and increments by 1 per chunk.
- Chunks must be sent in order. Lost / reordered chunks abort the transfer.
- Writes are *without response* for throughput. The peripheral signals
  back-pressure by emitting an UPC notification with
  `{"status":"pause","seq":N}` — the app pauses until it sees
  `{"status":"resume","seq":N}`.

### 3. Client → UPC: end

```json
{ "id": "u1", "op": "end", "data": { "upload_id": "abc123" } }
```

Peripheral validates SHA-256, then bridges to Flask. Final response:
```json
{
  "id": "u1",
  "status": "ok",
  "data": { "instance_name": "Sunset photo", "displayed": true }
}
```

### 4. Abort

The app may write `{"op":"abort","data":{"upload_id":"abc123"}}` to UPC at any
time. The peripheral drops the partial buffer.

## Security (v1)

- **JustWorks pairing, silent.** The Pi accepts incoming bond requests
  from any central via a `NoInputNoOutput` agent
  (`src/ble/pairing_agent.py`). No PIN, no confirmation UI on the Pi.
  Android may show a one-time "Pair?" prompt on first connect; tapping
  Pair completes the bond and Android remembers the device, so the
  prompt does not return on later connects.
- **No characteristic-level encryption requirement.** All GATT
  characteristics use plain `readable` / `writeable` permissions, so a
  client that *declined* bonding can still talk to the Pi. Pairing
  exists purely to keep Android from re-prompting the user, not as a
  security gate. The protocol's actual threat model matches the web
  UI's: open access on the local network.
- The hotspot mode generates an 8-character WPA2 password at first boot
  and stores it in `device.json`. The current password is included in
  the INFO payload, so a paired-once client knows it.
- A future version will gate writes behind a PIN-based bond. Track in
  GitHub issues.
